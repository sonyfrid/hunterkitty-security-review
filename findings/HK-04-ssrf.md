## Что не так
Если пост короткий, бот открывает ссылку из него и дочитывает вакансию на странице. Ссылку может написать кто угодно. Проверка была неполной:
- проверялся только первый адрес, а дальше запрос сам шёл по редиректам;
- использовалось `ip.is_private`, которое не считает внутренними, например, сеть 100.64.0.0/10;
- между проверкой адреса и соединением DNS мог поменять ответ (DNS rebinding).

## Чем опасно
Сервер мог сходить на внутренний адрес: сервисы на localhost, метаданные облака, соседние машины. Ответ попадал бы в текст вакансии.

## Как воспроизвёл
Разбор кода и юнит-тесты с подменённым DNS. На боевой сервер запросы не отправлял.

## Как исправлено
- `ip.is_global` вместо `is_private`, IPv4 внутри IPv6 (`::ffff:127.0.0.1`) разворачивается и проверяется как IPv4;
- редиректы ведутся вручную, не больше 3, каждый новый адрес проверяется заново;
- свой резолвер проверяет адрес ещё раз в момент соединения.

```python
def fixed_ip_ok(raw):
    ip = ipaddress.ip_address(raw.split("%", 1)[0])
    if isinstance(ip, ipaddress.IPv6Address) and ip.ipv4_mapped:
        ip = ip.ipv4_mapped
    return ip.is_global and not ip.is_multicast
```

## Проверка
`tests/test_ssrf.py`: внутренние, служебные и IPv4-mapped адреса блокируются, редирект на внутренний адрес не проходит, лишние редиректы и не-http схемы отклоняются. Уязвимая версия пропускает 100.64.0.0/10 и редирект (`xfail`). В продукте добавлен тест с настоящим локальным сервером, который отвечает редиректом.
