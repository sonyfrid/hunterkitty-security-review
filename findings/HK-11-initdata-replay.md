# HK-11. Перехваченную строку initData можно использовать повторно до суток

| | |
|---|---|
| Категория | OWASP API Top 10: API2 Broken Authentication; ASVS V3.3 (срок жизни сессии) |
| Серьёзность | Low, CVSS 3.1 ≈ 3.7 (AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N) |
| Компонент | проверка подписи Telegram Mini App |
| Кто нашёл | разбор после ревью кейса, 18.11.2026; повтор подтверждён тестом на стенде |
| Статус | принятый риск, план исправления ниже |

## Как устроено сейчас
Каждый запрос Mini App несёт заголовок `X-Telegram-Init-Data`. Сервер проверяет:
- подпись HMAC-SHA256 с ключом от токена бота, сравнение за постоянное время (`hmac.compare_digest` по байтам);
- возраст строки: не старше 24 часов и не из будущего (запас 5 минут, см. HK-02);
- id пользователя берётся только из проверенной подписи, параметры запроса на это не влияют;
- пользователь существует, не отключён.

Своей серверной сессии нет: каждый запрос проверяется заново по initData. Cookie не используются.

## Что не так
Подпись доказывает, что строку выдал Telegram, но не то, что её прислал тот же человек и впервые. Одну и ту же строку сервер принимает сколько угодно раз, пока ей меньше суток. Тест на стенде: два одинаковых запроса с одной строкой, оба 200 (`hunterkitty-e2e/tests/api/access.spec.js`, тест HK-11).

## Чем опасно и насколько реально
Чтобы воспользоваться, нужно сначала украсть саму строку. Она живёт в памяти страницы внутри Telegram и уходит только на наш сервер по HTTPS (TLS 1.3, `Referrer-Policy`, CSP запрещает чужие скрипты и запросы `connect-src 'self'`). Реальные пути утечки: вредоносное расширение в веб-версии Telegram, скриншот или запись экрана с открытыми инструментами разработчика, логи прокси при отладке. Украденная строка даёт доступ к аккаунту жертвы в Mini App до конца суток: фильтры, сохранённые вакансии, «О себе». Платёжные данные через Mini App не проходят.

Поэтому серьёзность низкая, но окно в сутки шире, чем нужно.

## Почему сутки
Mini App открывают утром и листают вечером, а Telegram не обновляет initData, пока страница открыта. Короткое окно без своей сессии выкидывало бы людей посреди работы.

## План исправления (минимальный, без переписывания)
1. **Своя короткая сессия после проверки Telegram.** Первый запрос `POST /api/session` с initData: сервер проверяет подпись, возраст не больше 10 минут, и выдаёт случайный токен (32 байта, `secrets.token_urlsafe`), который хранит в базе как хэш вместе с `tg_id`, временем выдачи и сроком 12 часов. Дальше страница шлёт `Authorization: Bearer <token>`, initData больше не ходит.
2. **initData одноразовая для обмена на сессию.** Сервер помнит хэш подписи (`hash`) использованных строк до истечения их срока и второй раз сессию по той же строке не выдаёт.
3. **Продление без повторного входа.** Если до конца сессии меньше часа, сервер выдаёт новый токен в ответе, старый отзывается. Отключение пользователя или выход сразу удаляют его сессии.
4. **Переход постепенный.** Старый путь по initData остаётся на время выкладки, но с окном 1 час, потом выключается.

Почему токен в заголовке, а не cookie: так не появляется CSRF (браузер сам не прикладывает заголовок к чужим запросам), а CORS у API нет.

## Проверка после исправления
- Повтор той же initData на `/api/session` даёт 401.
- Запрос со старым токеном после продления даёт 401.
- Отключённый пользователь теряет доступ сразу, а не через сутки.
