# HK-02. initData с датой из будущего не истекает

| | |
|---|---|
| Категория | OWASP API Top 10: API2 Broken Authentication |
| Серьёзность | Low, CVSS 3.1 ≈ 3.1 (AV:N/AC:H/PR:H/UI:N/S:U/C:L/I:L/A:N), защита в глубину |
| Компонент | проверка подписи Telegram Mini App |
| Кто нашёл | Сони, урок 2 курса AppSec, свой тест на стенде |

## Что не так
Mini App доверяет пользователю по строке initData, которую подписывает Telegram. Строка действует сутки. Проверка смотрела только в одну сторону: «не старше ли суток». Для даты из будущего возраст получается отрицательным, а отрицательное число всегда меньше суток, поэтому такая строка считалась свежей ещё год.

## Чем опасно и насколько реально
`auth_date` находится под подписью. Поставить дату из будущего может только тот, у кого есть токен бота, а с токеном атакующему эта дыра уже не нужна. Отдельно её не использовать, поэтому серьёзность низкая. Но если токен когда-нибудь утечёт и его сменят, строки «из будущего» не должны продолжать жить. Это дешёвая защита в глубину.

## Как воспроизвёл
На стенде с фальшивым токеном подписал initData с `auth_date` на год вперёд. Сервер вернул пользователя вместо отказа.

## Как исправлено
```python
age = time.time() - auth_date
if age > max_age or age < -CLOCK_SKEW_SECONDS:  # слишком старая ИЛИ из будущего
    return None
```
Запас 5 минут на расхождение часов Telegram и сервера.

## Проверка
`tests/test_auth_init_data.py::test_future_auth_date_rejected` зелёный, уязвимая версия падает (`xfail`). Небольшое расхождение часов по-прежнему пропускается.

## Вывод
Нашёл, оценил реальный риск как низкий и объяснил почему. Не каждая находка критическая, и это тоже надо уметь сказать.
